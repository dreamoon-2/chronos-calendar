# 给 Codex CLI 的开发任务提示词（整段可直接复制）

你现在是这个仓库的主工程师，负责把一个独立的跨端日程表真正开发成可以运行、测试和部署的 MVP，而不是只生成静态界面。

## 背景与目标

项目名 Chronos Calendar。使用 React + TypeScript + Vite + FullCalendar React v7 + Supabase（Auth / PostgreSQL / Realtime）+ PWA。产品参考 Android 日历的中文周视图：顶部年月与视图切换，周一到周日的日期列，独立全天栏，时间纵轴，彩色日程卡片，右下角“今天/新增”按钮。手机和电脑使用同一套代码，通过同一账号同步日程。

**首先完整阅读 `docs/PROJECT_SPEC.md` 和 `supabase/migrations/202610080001_initial_schema.sql`，以设计文档中的 MVP 范围、数据库结构、验收标准为事实源。** 若仓库尚不存在这些文件，请提示我将随任务一起交付的文件复制进去；不要自行编造“已连接数据库”等状态。

## 必做功能

- 邮箱登录与退出；会话保持，登录后进入真实日历。
- 中文周、月、日视图，并提供移动端三日视图；周一为一周开始；今天高亮、当前时间线、上一段/下一段导航。
- 日程的新增、编辑、软删除、分类着色、备注、全天/跨天事件、时间冲突可并排显示。
- 桌面端拖拽与拉伸日程（失败 `revert()`）；移动端优先保障编辑表单，触屏拖拽可以渐进增强。
- 后端基于可见日期范围查询，正确包含跨越范围边界的事件，不加载整个历史库。
- 在数据库 `version` 基础上实现乐观并发控制；若版本过期，刷新并提示冲突，不得静默覆盖。
- 事件和分类 Realtime 订阅：收到变化后使相关查询失效并重取；浏览器焦点恢复和网络恢复后兜底同步；登出移除通道与缓存。
- 移动/桌面适配、可读颜色、加载/空态/错误提示、表单校验；PWA 图标、manifest、安装与更新提示。
- 断网时提示“当前无法保存”，不要实现假的离线成功；不缓存认证 API 响应。
- README：启动命令、Supabase 配置、数据库迁移、Realtime publication、Auth 邮箱重定向、测试与部署说明。

## 特别容易做错的点（必须检查）

1. FullCalendar **all-day end exclusive**：全天一天 `2026-10-08` 到 `2026-10-09`；数据库全天用 `DATE` 而不是 UTC timestamp。
2. 分时事件用 `timestamptz`；支持跨午夜；不把日程错误映射到本地前一天。
3. FullCalendar 的视图区间是 `[start, end)`；查询条件必须做区间重叠，不能只查起点落在区间里的事件。
4. 删除是更新 `deleted_at`，不是 SQL DELETE。查询排除已删除；Realtime 订阅不能过滤掉已删除状态导致丢失通知。
5. 写入时加 `.eq('version', oldVersion)` 并 `.select()` 检查有无返回记录；数据库触发器自动增加版本号。
6. 分类归属通过数据库复合外键隔离，用户 A 的事件不能引用用户 B 的分类。
7. 组件卸载、登出或切换账户时必须释放 Realtime 订阅。
8. PWA 更新不要强行刷新正在编辑的页面；离线首版不允许假保存。
9. 不能将 service_role key 放进前端环境变量；`.env.local` 加入 gitignore，只提交 `.env.example`。
10. 若数据库迁移执行错误，定位 PostgreSQL/Supabase 的实际错误并修复 SQL，不跳过表/策略/索引/触发器。

## 工程结构建议

遵循 `docs/PROJECT_SPEC.md` 里的目录结构，保证：
- `features/calendar`：日历 UI 和视图区间；
- `features/events`：编辑表单、映射、查询、变更、Realtime；
- `features/categories`：分类 CRUD 与颜色；
- `features/auth`：认证；
- `lib`：Supabase 客户端、日期工具；
- `supabase/migrations`：可重复执行的版本化迁移流程（单条迁移只应用一次）；
- `tests/unit` 与 `tests/e2e`：测试。

不要把状态管理、数据库请求、表单逻辑和 Calendar 配置全部塞进一个组件里。组件与业务逻辑要分层，但也不要人为制造大量空文件。

## 执行步骤与验收

**M0 基础**：检测仓库、初始化 Vite/React/TS，完成 lint、typecheck、build 脚本，锁定依赖；没有凭证时提供清楚的配置提示和演示模式。

**M1 界面**：先基于参考布局创建真实可交互的周/月/日/三日界面，表单、分类颜色、全天与跨天展示、拖拽；完成手机端窄屏测试。

**M2 后端**：迁移 PostgreSQL、创建 RLS、配置 Auth、生成或定义 TypeScript 类型、对接事件和分类 CRUD；SQL/客户端接口行为均要确认。

**M3 同步**：将数据库变更通告转成可见区间的查询失效；实现网络恢复/前台恢复、并发版本控制与错误回滚；使用两个账号核验数据隔离。

**M4 发布**：接入 vite-plugin-pwa，制作合法 PNG 图标和安装 manifest，处理版本更新和网络状态，编写可部署的说明。

**M5 测试**：重点覆盖日期边界、跨午夜、全天 exclusive end、查询区间重叠、软删除、并发冲突与 RLS。运行 `npm run build`、`npm run lint`、`npm run typecheck`、`npm run test`；若可运行 Playwright 和 Supabase 本地环境，也运行 e2e/数据库测试。

验收的关键场景：同一个账号在手机和电脑分别打开；在电脑新增日程，手机出现；手机修改，电脑更新；删除后两端消失；断线重连后数据一致；并发修改有冲突提示；另一个账号看不到也改不了这些数据。**无法实际执行的测试必须明确说“未验证”，不得模拟通过。**
